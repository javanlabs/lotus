How scoring works

Every project gets one number out of 100 — its Lotus score. This page explains where that number comes from and what actually moves it.

The short version

Lotus reads four tools you already use — GitLab, SonarQube, Trivy and Sentry — and turns each one into its own score out of 100. Those four combine into a score for each repository, and the repositories combine into the project's Lotus score.

Nothing here is a judgement Lotus invents. Every number traces back to something one of those four tools already reported about your code.

The four inputs

Each is scored 0–100 on its own, then coloured green, amber or red by a separate rule — so a repository can hold a decent score and still be red, if the thing that turns it red is a pass-or-fail matter.

GITLAB · PIPELINES

The score averages two things: your pipeline success rate, and branch hygiene — the share of branches that have seen a commit recently. If 9 of your last 10 pipelines passed (90) but only half your branches are alive (50), that's (90 + 50) ÷ 2 = 70.

Colour: green when the most recent pipeline passed, red when it failed, amber while one is still running.
To raise it: fix what makes pipelines fail — a flaky test that fails one run in five costs 20 points on that half — and delete or merge branches nobody has touched in weeks. A green pipeline no longer hides a branch graveyard.

SONARQUBE · CODE QUALITY

The quality gate dominates. First a base is built by averaging your test coverage with the worst of SonarQube’s three ratings — reliability, security, maintainability, where A is 100 down to E at 20 (those ratings are how SonarQube itself summarises bugs, vulnerabilities and code smells). Then the gate scales the whole thing: passed keeps it, a warning takes it to 75%, a failed gate cuts it in half.

Example: gate passed, 95% coverage, all ratings A → (95 + 100) ÷ 2 = 98. But 89% coverage with a failing gate → 89 × 0.5 = 44. No amount of coverage can push a failing project above 50 — the gate is the pass/fail verdict your own team configured, and good numbers elsewhere must not be able to rescue it.
Colour: follows the quality gate — green when it passes, red when it fails.
To raise it: get the gate passing first; nothing else moves the score as much. Then fix whatever drags your worst rating — one D among the three sets the grade — then write tests for code that has none.

TRIVY · VULNERABILITIES

Starts at 100. Each critical finding costs 20 points, each high costs 5. Medium and low findings are counted and shown, but cost nothing.

So one critical = 80. Two criticals = 60. One critical plus four highs = 60 as well.
Colour: red if there is any critical, amber if there is any high, green otherwise.
To raise it: criticals first — each is worth four highs. Most are fixed by bumping a dependency, not by changing your own code.

SENTRY · ERRORS IN PRODUCTION

The only one that isn't a simple count. Lotus adds up how much burden your unresolved issues represent, then converts that into a score — no burden is 100, and the score falls away as burden grows.

Three things decide an issue's weight:

  • How Sentry classifies it — escalating counts 5×, regressed 4×, new 2×, ongoing 1×. An issue getting worse right now hurts five times as much as one you already know about.
  • How often it fires — but on a log scale, so 1,000 events is roughly three times one event, not a thousand times.
  • How recently — an issue's weight halves every 7 days it goes unseen. An error that stopped happening fades on its own.

Colour: the score becomes a grade — A is 90+, B is 80+, C is 70+, D is 60+, E below that. A and B are green, C is amber, D and E are red.
To raise it: resolve escalating and regressed issues first. One escalating issue outweighs five ongoing ones.

From four scores to one

A repository's score is the average of whichever of the four are set up for it. A repository with only GitLab and SonarQube is averaged over those two — not penalised for the two it doesn't have.

A project's Lotus score takes one extra step. Lotus first averages each tool across every repository — all your GitLab scores together, all your SonarQube scores together — and only then averages those four results.

WHY THE EXTRA STEP

Say a project has ten repositories wired to GitLab but only one SonarQube key. Averaging everything in one go would let GitLab outvote SonarQube ten to one — and adding an eleventh repository would shift the project's health without anything about its quality changing. Averaging per tool first gives each tool you use an equal say, however many repositories report it.

Colours work the other way: worst wins. One red repository makes the project red, however healthy the rest are. A project's colour tells you whether anything needs attention; its score tells you how much.

A worked example

An imaginary project, Storefront, with three repositories. The numbers are chosen to make the arithmetic easy to follow — everything Lotus shows comes out of one grid, read in two different directions.

REPOSITORY GITLAB SONARQUBE TRIVY ITS SCORE
payment-api 90 30 60 60
web-app 90 – 90 90
worker 90 – – 90
AVERAGE 90 30 75

A dash means that tool isn’t set up for that repository — it is skipped, never counted as zero.

READ ACROSS A ROW → A REPOSITORY’S SCORE

Average the tools a repository reports.
payment-api: (90 + 30 + 60) ÷ 3 = 60
web-app: (90 + 90) ÷ 2 = 90  — the missing SonarQube is skipped, so it divides by 2
worker: 90 ÷ 1 = 90

READ DOWN THE COLUMNS ↓ THE PROJECT’S LOTUS SCORE

First average each tool across the repositories that report it:
GitLab: (90 + 90 + 90) ÷ 3 = 90
SonarQube: 30 ÷ 1 = 30
Trivy: (60 + 90) ÷ 2 = 75
Then average those three:
(90 + 30 + 75) ÷ 3 = 65  ← Storefront’s Lotus score

THE PART THAT SURPRISES PEOPLE

The Lotus score is not the average of the repository scores. That would be (60 + 90 + 90) ÷ 3 = 80 — a comfortable number that hides the real problem. The actual score is 65, because SonarQube’s lone 30 counts as a full third of the project, not as one-sixth of one repository. Coverage is bad wherever it is measured; the score says so instead of letting two repositories that don’t measure it drown that out. Fixing payment-api’s coverage — or adding coverage to the other two repos — is what moves this project.

Where to start

  1. Anything red. Red means a tool said this is failing right now — a broken pipeline, a failed quality gate, a critical vulnerability. These are usually also the cheapest to fix.
  2. Critical vulnerabilities. Worth 20 points each and usually one dependency bump away.
  3. Escalating Sentry issues. Weighted 5× and getting worse while you read this.
  4. Coverage on untested files. The slowest to move, but the one that stays moved.

A repository with no integration set up for a tool simply isn't measured on it — it shows as "no data" rather than as a zero. Connecting a tool can therefore move a score in either direction: it starts measuring something that was previously invisible.

Scores refresh after each sync. A change you make now shows up on the next collection run for that repository, not immediately.
